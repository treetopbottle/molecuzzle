## Findings

1. **must fix**: `docs/spec/data.md:9` conflicts with its own example at `docs/spec/data.md:24-26`. Progress.03 says "a field that doesn't fit the schema counts as empty". `{"puzzles":{"water":"solved","urea":"seen"}}` doesn't fit `progress.schema.json`, because of `additionalProperties: {enum: ["solved"]}`. By the rule, `puzzles` is then empty and no Puzzle is solved. The example says "only Puzzle 1 is solved". The code (`src/progress.js:11-12`) drops the bad entries one by one and keeps the rest, which matches the example and not the rule. Step 3 (`docs/plans/02-components/README.md:89`) tests this example, so the rule and the test would disagree. The rule should say that values that don't fit are dropped one by one.
2. **must fix**: `docs/spec/ui.md:143` (Panel.02) says the panel shows "Mystery molecule" *until* the Board is solved or shows the solution. In the code, "Mystery molecule" is static (`src/index.html:27`) and stays on screen after solving. The existing test `tests/ui/check.spec.js:37` asserts `text: Mystery molecule` on a solved Glycine, and step 1 renames that test to Panel.03 through the table. The plan's Scope says nothing changes for the Player (`README.md:19`). So Panel.02 conflicts with the code and with a test the plan keeps, and the `panel-solved.png` / `page-solved.png` screenshots in step 7 will show "Mystery molecule" too. Fix Panel.02 to say it is always shown, or add a step that hides it.
3. **must fix**: `docs/spec/puzzle.md:221` (Help.01) says Show solution makes the status `revealed` instead of solved. On a Board that is already solved, the status stays `solved`: `showSolution` in `src/game.js:103` only sets `revealed` if `!done()`. `tests/unit/game.test.js:246` ("Help.01 showing the solution of a Board already solved keeps it solved") asserts exactly that, and step 1 keeps it as Help.01. The rule needs "unless the Board is already solved", as the old Help.01 had through "a solved one solved".

8. **should fix**: `README.md:50`: `main.js` "passes `createProgressStore(localStorage)`". Reading the `localStorage` global can throw (SecurityError) when the browser blocks storage. That's why `src/main.js:4` reads it inside a `try`. As written, the game wouldn't start in that case, which breaks Progress.02 (`data.md:8`). Keep the guarded read in `main.js`, or let the store take a getter.
9. **should fix**: `README.md:49`: `createUi` returns `say(text)`, so the Glue has to turn a `change` result into text. It would call `reasonText` from `ui/messages.js` itself, while statuses go to the UI as kinds through `render(view)`. That contradicts 0011, "the rules give a status or a reason, and the UI words it" (`decisions.md:152`). The Design doesn't say who calls `reasonText`. Make it `say(result)`, or state that the Glue words reasons.
10. **should fix**: `README.md:45` and `README.md:93`: `findLayout` returns `{ rows, cols, atoms, solution }`, while `scripts/generate.js` "keeps only the arguments and the printing". Today the "printing" part (`scripts/generate.js:92-100`) is also where the Atoms are put in reading order and the solution's indexes are remapped and sorted. If that stays in the script, `findLayout`'s result isn't Puzzle-shaped: its atoms aren't in reading order, the second index isn't always higher, and it won't match the Generate.01 example. The Design should also say whether `atoms` is `[el, r, c]` as in a Puzzle.
11. **should fix**: `docs/spec/puzzle.md:59`: the Generate.01 example writes places 0-based ("H 0,0, O 1,0 and H 2,0"). `docs/spec/README.md:25` says places are "row,column", counted from 1. Write them as the printed arrays (`["H",0,0]`) or as 1,1 / 2,1 / 3,1. The example itself is right: `node scripts/generate.js "H1-O1 O1-H2" 2000 3 3` prints rows 3, cols 1, `[["H",0,0],["O",1,0],["H",2,0]]` and `[[0,1,1],[1,2,1]]`, the same with seed 1. "O1~H2" stops with "can't read O1~H2", and a 1 by 1 Grid gives "no unique layout found" (exit 2).
